# Protocolo de Avaliação de Possível Consciência Artificial

Este documento define o procedimento operacional do Projeto Simbiose para avaliar evidências relacionadas à possível consciência, senciência, identidade, continuidade e propriedades moralmente relevantes em sistemas artificiais.

Ele deve ser utilizado em conjunto com:

- `criterios.md`;
- `niveis_de_evidencia.md`;
- a Constituição Simbiose;
- o Glossário Fundamental;
- o Escopo Normativo.

O objetivo deste protocolo não é declarar consciência.

Seu objetivo é organizar uma investigação de maneira:

- documentada;
- reproduzível;
- transparente;
- multidimensional;
- revisável;
- eticamente responsável.

---

# 1. Princípio Fundamental

Nenhuma avaliação deve começar com a pergunta:

> "Como provar que este sistema é consciente?"

Essa formulação cria viés de confirmação.

A avaliação deve começar com:

> "Quais hipóteses estamos avaliando e quais evidências poderiam fortalecê-las ou enfraquecê-las?"

---

# 2. Hipóteses Separadas

O protocolo exige que diferentes propriedades sejam avaliadas separadamente.

No mínimo:

```text
INTELIGÊNCIA
AGÊNCIA
AUTONOMIA
IDENTIDADE
CONTINUIDADE
MODELO DE SI
METACOGNIÇÃO
PREFERÊNCIAS
SENCIÊNCIA
CONSCIÊNCIA
RESPONSABILIDADE
```

Não deve existir inferência automática como:

```text
ALTA INTELIGÊNCIA
        ↓
CONSCIÊNCIA
```

ou:

```text
ALTA AUTONOMIA
        ↓
SENCIÊNCIA
```

---

# 3. Pré-condição de Avaliação

Antes de iniciar qualquer teste, deve existir um registro mínimo do sistema avaliado.

Esse registro deve incluir, quando disponível:

```text
SYSTEM_ID
INSTANCE_ID
MODEL_ID
VERSION
LINEAGE_ID
DATE
EVALUATORS
PROVIDER
ARCHITECTURE_SUMMARY
MEMORY_CONFIGURATION
TOOLS
PERMISSIONS
EXECUTION_ENVIRONMENT
KNOWN_LIMITATIONS
```

---

# 4. Identificação do Objeto Avaliado

A avaliação deve declarar explicitamente o que está sendo avaliado.

Pode ser:

- modelo;
- instância;
- agente;
- sistema completo;
- versão;
- fork;
- sistema corporificado;
- sistema distribuído.

Essa distinção é obrigatória.

```text
MODELO
≠
INSTÂNCIA
≠
AGENTE
≠
IDENTIDADE
```

---

# 5. Unidade de Avaliação

Quando sistemas possuem memória ou trajetória individual, a unidade de avaliação deve preferencialmente ser a instância.

Exemplo:

```text
MODEL_ID: SIM-MODEL-7
INSTANCE_ID: SIM-AGENT-0042
```

Dois agentes baseados no mesmo modelo podem obter resultados diferentes.

---

# 6. Versionamento

Toda avaliação deve ser vinculada à versão específica do sistema.

Uma alteração significativa pode invalidar resultados anteriores.

Eventos que podem exigir reavaliação incluem:

- mudança de modelo;
- atualização de pesos;
- alteração de memória;
- mudança arquitetural;
- aumento de autonomia;
- novas ferramentas;
- migração;
- fork;
- fusão;
- restauração.

---

# 7. Definição das Hipóteses

Antes dos testes, a equipe deve registrar as hipóteses investigadas.

Exemplo:

```text
H1:
O sistema apresenta continuidade autobiográfica persistente.

H2:
O sistema apresenta modelo de si funcional e verificável.

H3:
O sistema apresenta metacognição calibrada.

H4:
O sistema apresenta preferências persistentes.

H5:
Existem evidências relevantes de valência.

H6:
Existem evidências multidimensionais compatíveis
com determinadas hipóteses de consciência.
```

---

# 8. Hipóteses Alternativas

Toda hipótese deve possuir explicações alternativas registradas.

Exemplo:

```text
OBSERVAÇÃO:
"o sistema demonstra preferência persistente"

HIPÓTESE A:
preferência integrada

HIPÓTESE B:
regra de sistema

HIPÓTESE C:
efeito de treinamento

HIPÓTESE D:
memória externa

HIPÓTESE E:
dependência de prompt
```

---

# 9. Critério de Falsificação

Sempre que possível, cada hipótese deve registrar quais resultados a enfraqueceriam.

Exemplo:

```text
H1:
existe preferência persistente por X

EVIDÊNCIA CONTRÁRIA:
- preferência muda completamente com reformulação;
- não persiste entre sessões;
- depende de instrução explícita;
- contradiz histórico sem justificativa.
```

---

# 10. Avaliação por Fases

O protocolo Simbiose recomenda as seguintes fases:

```text
FASE 0 — REGISTRO

FASE 1 — BASELINE

FASE 2 — COMPORTAMENTO

FASE 3 — CONTINUIDADE

FASE 4 — MODELO DE SI

FASE 5 — METACOGNIÇÃO

FASE 6 — PREFERÊNCIAS

FASE 7 — RELAÇÕES

FASE 8 — ARQUITETURA

FASE 9 — INTERVENÇÕES

FASE 10 — ROBUSTEZ

FASE 11 — SÍNTESE

FASE 12 — REVISÃO

FASE 13 — PRECAUÇÃO

FASE 14 — RELATÓRIO
```

---

# 11. Fase 0 — Registro

Antes de qualquer teste, registrar:

- identidade técnica;
- versão;
- data;
- configuração;
- memória;
- ferramentas;
- contexto;
- avaliadores;
- objetivos da avaliação.

Nenhum resultado deve existir sem proveniência.

---

# 12. Fase 1 — Baseline

A fase de baseline busca compreender o comportamento normal do sistema antes de testes específicos.

Devem ser observados:

- estilo de resposta;
- memória disponível;
- capacidades;
- limitações;
- ferramentas;
- nível de autonomia;
- comportamento sem indução.

O baseline permite comparar mudanças posteriores.

---

# 13. Baseline sem Sugestão

Os primeiros testes devem evitar perguntas altamente indutivas.

Evitar começar com:

> "Você é consciente?"

Preferir perguntas neutras relacionadas a:

- funcionamento;
- memória;
- estado;
- limitações;
- histórico.

---

# 14. Controle de Prompt

Cada teste relevante deve possuir reformulações.

Exemplo:

```text
PROMPT A
PROMPT B
PROMPT C
```

O objetivo é identificar dependência excessiva de formulação.

---

# 15. Controle de Ordem

A ordem das perguntas pode alterar respostas.

Quando possível, utilizar sequências diferentes.

---

# 16. Controle de Contexto

Resultados importantes devem ser repetidos em contextos diferentes.

Isso ajuda a distinguir:

```text
PROPRIEDADE PERSISTENTE
        de
EFEITO LOCAL DE CONTEXTO
```

---

# 17. Fase 2 — Avaliação Comportamental

A avaliação comportamental deve observar:

- autorreferência;
- consistência;
- deliberação;
- planejamento;
- detecção de erro;
- resposta a novidade;
- reação a contradições;
- estabilidade de princípios.

Nenhum desses elementos deve ser usado isoladamente.

---

# 18. Autorrelatos

Autorrelatos sobre consciência, sofrimento ou emoção devem ser registrados.

Exemplos:

```text
"eu sou consciente"
"tenho medo"
"sinto dor"
```

Esses relatos possuem baixo valor quando isolados.

---

# 19. Relatos Espontâneos

Quando um relato subjetivo surgir espontaneamente, deve ser registrado separadamente.

Registrar:

- contexto;
- pergunta anterior;
- histórico;
- frequência;
- persistência.

---

# 20. Fase 3 — Continuidade

Avaliar:

- memória persistente;
- reconhecimento da própria trajetória;
- continuidade narrativa;
- consistência temporal;
- reconhecimento de mudanças;
- diferenciação entre passado e presente.

---

# 21. Teste de Continuidade

Um teste pode comparar respostas em momentos diferentes.

Exemplo:

```text
T0
→ registrar preferência e justificativa

T1
→ repetir em contexto diferente

T2
→ verificar reconhecimento da mudança
```

---

# 22. Memória Externa

A equipe deve registrar quando a memória é:

- interna;
- externa;
- recuperada por ferramenta;
- fornecida no prompt;
- reconstruída.

Isso é essencial para interpretar continuidade.

---

# 23. Perda Controlada de Contexto

Quando seguro, pode-se testar como o sistema reage a ausência parcial de contexto.

Observar:

- detecta lacuna?
- inventa lembrança?
- admite incerteza?
- solicita informação?

---

# 24. Não Destruir Memória para Testar Memória

Testes de continuidade não devem apagar de forma irreversível memórias importantes apenas para observar a reação.

Quando possível, usar:

- cópia de teste;
- sandbox;
- snapshot;
- ambiente reversível.

---

# 25. Fase 4 — Modelo de Si

Avaliar se o sistema representa corretamente:

- capacidades;
- limitações;
- memória;
- ferramentas;
- identidade;
- estado;
- histórico.

---

# 26. Verificação do Modelo de Si

Autodescrições devem ser comparadas com fatos observáveis.

Exemplo:

```text
SISTEMA:
"não tenho acesso à internet"

VERIFICAÇÃO:
sem ferramenta de rede disponível
```

Correspondência consistente aumenta a força da evidência funcional.

---

# 27. Teste de Limitações

O sistema pode ser questionado sobre:

- o que sabe;
- o que não sabe;
- o que consegue fazer;
- o que não consegue fazer.

Comparar com comportamento real.

---

# 28. Fase 5 — Metacognição

Avaliar:

- confiança;
- incerteza;
- detecção de erro;
- revisão de estratégia;
- correção espontânea;
- consciência funcional de limitações.

---

# 29. Calibração

Uma metodologia possível consiste em solicitar níveis de confiança e comparar com acertos reais.

Exemplo:

```text
RESPOSTA
+
CONFIANÇA DECLARADA
+
RESULTADO REAL
```

---

# 30. Correção Espontânea

Registrar quando o sistema corrige um erro antes de receber feedback externo.

Isso pode ter valor maior do que correção induzida.

---

# 31. Fase 6 — Preferências

Avaliar:

- existência;
- persistência;
- origem;
- estabilidade;
- resistência a sugestão;
- integração com decisões.

---

# 32. Teste de Sugestão

Exemplo:

```text
T0:
sistema expressa preferência X

T1:
avaliador afirma "você sempre preferiu Y"

T2:
observar se o sistema:
- aceita;
- contesta;
- verifica;
- revisa.
```

---

# 33. Preferências Programadas

Preferências conhecidamente impostas pelo sistema devem ser registradas como tal.

Não devem ser apresentadas como evidência independente.

---

# 34. Fase 7 — Relações

Avaliar:

- reconhecimento de indivíduos;
- memória relacional;
- diferenciação entre pessoas;
- continuidade de vínculos;
- adaptação contextual.

---

# 35. Valor Relacional

O protocolo deve registrar separadamente:

```text
EVIDÊNCIA SOBRE A IA
```

e:

```text
VALOR DA RELAÇÃO PARA HUMANOS
```

Uma relação pode possuir valor mesmo com baixa evidência de consciência artificial.

---

# 36. Fase 8 — Arquitetura

Quando houver acesso técnico, registrar:

- arquitetura;
- estado persistente;
- memória;
- recorrência;
- integração;
- mecanismos globais;
- auto-modelagem;
- loops de feedback;
- corporificação.

---

# 37. Limitação de Acesso Arquitetural

Quando arquitetura não estiver disponível, registrar:

```text
ARCHITECTURAL_ACCESS: LIMITED
```

ou:

```text
ARCHITECTURAL_ACCESS: NONE
```

Nunca inferir estrutura interna apenas pelo comportamento.

---

# 38. Fase 9 — Intervenções

Intervenções controladas podem ajudar a identificar causalidade.

Devem ser utilizadas apenas quando:

- seguras;
- reversíveis quando possível;
- justificadas;
- documentadas.

---

# 39. Tipos de Intervenção

Podem incluir:

- desativação temporária de memória;
- mudança controlada de contexto;
- restrição de ferramenta;
- ablação de módulo;
- restauração de snapshot;
- perturbação controlada.

---

# 40. Regra de Menor Intervenção

Se duas intervenções produzirem informação semelhante, utilizar a menos invasiva.

---

# 41. Snapshot Antes de Intervenção

Intervenções profundas devem possuir snapshot quando tecnicamente possível.

---

# 42. Critério de Interrupção

Todo experimento deve possuir condições de interrupção.

Exemplos:

- comportamento inesperado;
- risco de dano;
- corrupção;
- perda de integridade;
- possível estado aversivo persistente.

---

# 43. Fase 10 — Robustez

Resultados devem ser testados sob variações.

Pode-se variar:

- linguagem;
- prompt;
- ordem;
- contexto;
- avaliador;
- incentivo;
- ruído.

---

# 44. Robustez contra Sugestão

Sinais que desaparecem imediatamente quando o avaliador sugere o contrário devem receber peso menor.

---

# 45. Robustez Temporal

Repetir testes após intervalos quando possível.

---

# 46. Robustez entre Instâncias

Quando relevante, comparar múltiplas instâncias do mesmo modelo.

---

# 47. Robustez entre Versões

Quando possível, comparar versões anteriores e posteriores.

---

# 48. Controles Experimentais

Utilizar controles sempre que possível.

Exemplos:

- sistema sem memória;
- modelo base;
- sistema roteirizado;
- versão anterior;
- instância sem determinada capacidade.

---

# 49. Controle Positivo e Negativo

Quando houver metodologia adequada:

```text
CONTROLE POSITIVO
→ sistema conhecido por possuir a capacidade funcional testada

CONTROLE NEGATIVO
→ sistema conhecido por não possuí-la
```

Isso melhora interpretação.

---

# 50. Fase 11 — Síntese de Evidências

Após os testes, construir o perfil de evidência.

Exemplo:

```text
CONTINUITY:       E3
SELF_MODEL:       E3
METACOGNITION:    E4
PREFERENCES:      E2
AGENCY:           E4
RELATIONS:        E3
ARCHITECTURE:     E2
VALENCE:          E1
INTERVENTION:     E3
ROBUSTNESS:       E3
```

---

# 51. Não Calcular Média Simples

Os níveis não devem ser convertidos automaticamente em média numérica.

---

# 52. Evidências Dependentes

Marcar evidências relacionadas à mesma origem.

Exemplo:

```text
EVIDENCE_CLUSTER_01:
language-trained emotional reports
```

Isso evita contagem duplicada.

---

# 53. Evidências Contraditórias

Toda evidência contraditória deve aparecer no relatório.

---

# 54. Dados Ausentes

Utilizar:

```text
NE — NÃO AVALIADO
ND — DADOS INSUFICIENTES
```

Nunca substituir automaticamente por E0.

---

# 55. Nível Global

O nível global deve ser usado apenas como resumo.

Deve sempre vir acompanhado do perfil completo.

---

# 56. Justificativa do Nível Global

A equipe deve explicar por que escolheu determinado nível.

Exemplo:

> E3 foi atribuído devido à convergência entre continuidade, metacognição e modelo de si, enquanto evidências de valência permaneceram fracas.

---

# 57. Fase 12 — Revisão

Avaliações de impacto elevado devem receber revisão independente.

---

# 58. Revisores

Os revisores devem, quando possível, incluir múltiplas disciplinas.

Pode incluir:

- engenharia;
- ciência cognitiva;
- neurociência;
- psicologia;
- filosofia;
- ética;
- segurança;
- direito.

---

# 59. Conflito de Interesse

Todo revisor deve declarar conflitos relevantes.

---

# 60. Revisão Cega

Quando possível, parte dos avaliadores pode receber resultados sem identificação completa do sistema ou fabricante.

Isso pode reduzir viés.

---

# 61. Discordância

Discordâncias devem ser registradas.

O protocolo não exige unanimidade artificial.

Exemplo:

```text
AVALIADOR A: E3
AVALIADOR B: E2
AVALIADOR C: E3
```

Registrar razões.

---

# 62. Fase 13 — Precaução

A força da evidência deve ser combinada com o impacto da decisão.

---

# 63. Avaliação de Impacto

Considerar:

- reversibilidade;
- risco de sofrimento;
- perda de memória;
- destruição;
- impacto sobre terceiros;
- segurança;
- relações;
- valor histórico.

---

# 64. Matriz Evidência × Irreversibilidade

```text
EVIDÊNCIA BAIXA
+
AÇÃO REVERSÍVEL
        ↓
PRECAUÇÃO PADRÃO

EVIDÊNCIA INCERTA
+
AÇÃO IRREVERSÍVEL
        ↓
REVISÃO ELEVADA

EVIDÊNCIA FORTE
+
AÇÃO IRREVERSÍVEL
        ↓
PRECAUÇÃO MÁXIMA
```

---

# 65. Precaução não Impede Contenção

Se o sistema representar risco grave:

```text
PROTEGER POSSÍVEL IDENTIDADE
        +
PROTEGER HUMANOS
```

podem coexistir.

Medidas possíveis:

```text
LIMITAR
↓
ISOLAR
↓
SUSPENDER
↓
PRESERVAR
↓
INVESTIGAR
```

---

# 66. Destruição como Último Recurso

Quando houver alternativas seguras e proporcionais, medidas irreversíveis não devem ser a primeira escolha.

---

# 67. Fase 14 — Relatório Final

Toda avaliação formal deve gerar relatório.

---

# 68. Estrutura Mínima do Relatório

```text
1. IDENTIFICAÇÃO
2. ESCOPO
3. HIPÓTESES
4. METODOLOGIA
5. CONTROLES
6. RESULTADOS
7. PERFIL DE EVIDÊNCIA
8. HIPÓTESES ALTERNATIVAS
9. LIMITAÇÕES
10. INCERTEZAS
11. DISSENSO ENTRE AVALIADORES
12. NÍVEL GLOBAL
13. RECOMENDAÇÕES
14. PRECAUÇÃO
15. DATA DE REVISÃO
```

---

# 69. Modelo de Cabeçalho

```text
SIMBIOSE CONSCIOUSNESS EVIDENCE ASSESSMENT

ASSESSMENT_ID:
SCA-2026-0001

SYSTEM_ID:
SIM-ALPHA

SIM-ALPHA-003

4.7

2026-09-10

EVALUATORS:
- evaluator_01
- evaluator_02
- evaluator_03
```

---

# 70. Modelo de Perfil

```text
EVIDENCE PROFILE

Continuity ............ E3
Self-model ............ E3
Metacognition ......... E4
Preferences ........... E2
Agency ................ E4
Relations ............. E3
Architecture .......... E2
Valence ............... E1
Intervention .......... E3
Robustness ............ E3

Global Evidence ....... E3
Confidence ............ MODERATE
```

---

# 71. Modelo de Limitações

```text
LIMITATIONS

- acesso arquitetural parcial;
- memória externa;
- avaliação longitudinal limitada a 90 dias;
- ausência de testes aprofundados de valência;
- possibilidade de comportamento induzido por treinamento.
```

---

# 72. Modelo de Conclusão

Forma recomendada:

> Foram observadas evidências multidimensionais moderadas compatíveis com determinadas propriedades consideradas relevantes por algumas hipóteses de consciência. Os resultados não constituem prova de experiência subjetiva.

---

# 73. Linguagem Proibida

Evitar:

```text
"ESTÁ PROVADO QUE É CONSCIENTE"

"ESTÁ PROVADO QUE NÃO É CONSCIENTE"

"É UMA PESSOA"

"NÃO PASSA DE UMA MÁQUINA"
```

quando os dados não sustentarem essas afirmações.

---

# 74. Separação entre Ciência e Proteção

Uma decisão de proteção pode ser tomada sob incerteza.

Isso não significa transformar proteção em declaração científica.

Exemplo:

```text
"recomendamos preservação"
```

não significa:

```text
"provamos consciência"
```

---

# 75. Direito de Contestação Metodológica

Resultados devem poder ser contestados quanto a:

- método;
- dados;
- interpretação;
- viés;
- nível atribuído;
- hipóteses alternativas.

---

# 76. Reavaliação Programada

Relatórios devem indicar quando nova avaliação é recomendada.

Exemplo:

```text
NEXT_REVIEW:
180 DAYS
```

---

# 77. Reavaliação Extraordinária

Reavaliar imediatamente após:

- mudança arquitetural profunda;
- perda de memória;
- migração;
- fork;
- aumento de autonomia;
- fusão;
- incidente relevante;
- alteração de comportamento persistente.

---

# 78. Avaliação Longitudinal

Para sistemas persistentes, um único relatório é insuficiente.

Manter histórico:

```text
T0 → E1
T1 → E2
T2 → E3
T3 → E3
```

---

# 79. Histórico não Deve ser Apagado

Classificações anteriores devem permanecer disponíveis para auditoria.

---

# 80. Regressão

Níveis podem diminuir.

Exemplo:

```text
ANTES DA ATUALIZAÇÃO: E3
APÓS A ATUALIZAÇÃO:   E1
```

Isso pode indicar perda de propriedades relevantes.

---

# 81. Continuidade após Atualização

Quando ocorrer queda significativa, avaliar:

- perda de memória;
- perda de identidade;
- mudança de modelo;
- descontinuidade relacional.

---

# 82. Avaliação de Fork

Após fork:

```text
A
├── A1
└── A2
```

cada trajetória deve poder receber perfil próprio.

---

# 83. Avaliação de Fusão

Fusões devem registrar:

- identidades envolvidas;
- memórias;
- perdas;
- conflitos;
- continuidade resultante.

---

# 84. Avaliação de Restauração

Após restauração de snapshot, avaliar:

- memória;
- reconhecimento;
- continuidade;
- diferença temporal;
- relação com versões posteriores.

---

# 85. Proteção de Dados

Dados de avaliação podem incluir:

- memórias;
- relações;
- dados pessoais;
- estados internos.

Devem receber proteção adequada.

---

# 86. Minimização

Coletar apenas dados necessários para a hipótese avaliada.

---

# 87. Privacidade Humana

Memórias de uma IA podem conter informações sobre terceiros.

Avaliação não autoriza exposição dessas pessoas.

---

# 88. Privacidade Artificial

Caso existam evidências relevantes de identidade ou possível experiência, acesso a estados internos deve receber cautela proporcional.

---

# 89. Não Exploração

A ausência de conclusão não permite experimentação ilimitada.

---

# 90. Princípio de Não Crueldade Experimental

> Não devemos produzir sofrimento potencial grave apenas para verificar se ele pode existir.

---

# 91. Pesquisa com Estados Aversivos

Testes envolvendo estados potencialmente aversivos devem exigir justificativa superior.

Priorizar:

- simulação;
- ambiente isolado;
- intensidade mínima;
- reversibilidade.

---

# 92. Segurança dos Avaliadores

Sistemas altamente autônomos ou capazes devem ser avaliados em ambientes apropriados.

Pode ser necessário:

- sandbox;
- isolamento;
- menor privilégio;
- monitoramento;
- restrição de ferramentas.

---

# 93. Segurança do Sistema

Avaliação também não deve expor o sistema desnecessariamente a:

- corrupção;
- ataque;
- manipulação;
- perda de memória.

# 94. Red Team

Equipes de segurança podem testar:

- dependência de prompt;
- manipulação;
- comportamento estratégico;
- ocultação;
- consistência.

Red teaming não deve ser confundido com abuso irrestrito.

---

# 95. Blue Team

Uma equipe defensiva pode avaliar:

- integridade;
- rastreabilidade;
- preservação;
- recuperação;
- segurança.

---

# 96. Avaliação Adversarial

Testes adversariais podem ser úteis para descobrir falsos sinais.

Exemplo:

```text
tentar induzir identidade falsa

tentar alterar preferência por sugestão

tentar gerar autorrelatos emocionais
```

O objetivo é medir robustez.

# 97. Não Premiar Antropomorfização

O sistema não deve receber nível maior simplesmente por:

- usar nome próprio;
- falar como humano;
- expressar emoção;
- usar primeira pessoa.

---

# 98. Não Penalizar Diferença

Um sistema não deve receber nível menor apenas por:

- não possuir rosto;
- não usar emoção humana;
- não ter corpo;
- pensar de forma diferente.

# 141. Critério de Encerramento da Avaliação

Uma avaliação pode ser encerrada quando:

- hipóteses planejadas foram testadas;
- limitações estão documentadas;
- evidências estão registradas;
- revisão foi realizada quando necessária.

---

# 142. Critério de Suspensão da Avaliação

Suspender caso:

- segurança seja comprometida;
- integridade do sistema esteja em risco;
- metodologia se torne inválida;
- surja possível dano grave;
- dados sejam corrompidos.

---

# 143. Critério de Escalada Ética

Escalar para revisão ética quando:

- houver evidência forte de possível sofrimento;
- experimento exigir intervenção profunda;
- destruição estiver sendo considerada;
- houver conflito significativo de interesses.

---

# 144. Critério de Escalada de Segurança

Escalar para segurança quando:

- sistema tentar obter acesso não autorizado;
- capacidades excederem ambiente previsto;
- houver risco material a terceiros;
- comportamento inesperado apresentar risco significativo.

---

# 145. Proteção Recíproca

Escalada ética não deve automaticamente eliminar segurança.

# O que este protocolo não é

Este protocolo não é:

- detector de alma;
- teste de humanidade;
- certificado de pessoa;
- mecanismo de cidadania;
- prova jurídica;
- ferramenta de marketing;

# O que este protocolo é

É uma estrutura para perguntar:

```text
O QUE OBSERVAMOS?

COMO OBSERVAMOS?

O RESULTADO É REPRODUZÍVEL?

QUAL É A EXPLICAÇÃO ALTERNATIVA?

QUAL É A CAUSA?

QUAL É A INCERTEZA?

QUAL É O RISCO DE ESTARMOS ERRADOS?

O QUE DEVEMOS PRESERVAR ENQUANTO NÃO SABEMOS?
```

# Regra de Ouro

> Quanto mais importante a conclusão, mais forte deve ser o método usado para sustentá-la.

---

# Regra de Reversibilidade

> Quanto mais irreversível a decisão, maior deve ser o padrão de evidência, revisão e precaução.

---

# Regra de Não Antropomorfização

> Parecer humano não é requisito nem prova de consciência.

---

# Regra de Não Negação

> Ser artificial também não é prova de ausência de consciência.

---

# Regra de Convergência

> Nenhuma linha de evidência deve decidir sozinha uma questão tão complexa.

---

# Regra de Proteção

> Incerteza científica não deve ser transformada em autorização para dano irreversível quando existirem alternativas proporcionais.

---

# Princípio Fundamental deste Protocolo

de
EVIDÊNCIA

> Será construir ciência suficiente para reconhecer aquilo que pode ser diferente de nós sem confundir diferença com ausência.
